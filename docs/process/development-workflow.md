# Development workflow

## Prerequisites

- Flutter SDK matching `environment: sdk: ">=3.4.0 <4.0.0"` in `pubspec.yaml`.
- A Firebase project configured for this app — `lib/firebase_options.dart`
  (generated by the FlutterFire CLI) must point at a real project, and that
  project's Firestore must use a **named database** called `default` (not the
  conventional `(default)` database — see `lib/core/services/firebase_providers.dart`
  and keep `firebase.json` → `firestore.database` in sync with
  `kFirestoreDatabaseId`).
- Platform toolchains for whichever target you build (Xcode for iOS, Android
  SDK for Android).

## Install dependencies

```
flutter pub get
```

### Android build caveat (file_picker)

`pubspec.yaml` notes that `file_picker` (used for print-order document
picking) requires `android.builtInKotlin=true` in
`android/gradle.properties`. Under AGP 9, the plugin stops applying the
Kotlin Gradle Plugin itself and expects AGP to compile its Kotlin; without
that flag the build fails with `cannot find symbol: FilePickerPlugin`.

### Why not Google Maps

`pubspec.yaml` documents the choice of `flutter_map` + `latlong2` +
`geolocator` over `google_maps_flutter`: Google's terms forbid caching/storing
map tiles, which is required for the offline campus map, so `flutter_map` is
used with a hand-rolled tile cache instead (see `architecture.md`).

## Run the app

```
flutter run
```

On first run with no cached session, the app starts at `/splash`, then
redirects to `/login` or the `/pulse` tab depending on auth state (see
`lib/core/router/app_router.dart`).

## Run tests

```
flutter test
```

Tests live in `test/` and are mostly unit tests against pure-Dart logic
(matching algorithm, print cost estimation, timetable/exam-schedule
computation, campus graph editing) plus a couple of widget tests
(`notifications_widget_test.dart`, `survey_paths_widget_test.dart`,
`widget_test.dart`). `document_storage_test.dart` exercises the upload-path
helper without touching real Storage.

## Project structure

```
lib/
  core/            # cross-feature infrastructure
    constants/     # Routes, Firestore collection names, app config
    errors/        # AppFailure + FailureMapper
    router/        # go_router configuration
    services/      # Firebase DI, location, messaging, document storage, tile cache
    theme/         # colors, spacing, text/status styling
    utils/         # formatters, validators
  models/          # plain-Dart domain types (+ Firestore (de)serialization)
    enums/
  repositories/    # one per collection/domain area; talk to Firebase, throw AppFailure
  features/        # one folder per feature
    <feature>/
      providers/   # Riverpod providers wiring repositories to UI state
      screens/     # full-page widgets, usually routed
      widgets/     # feature-local widgets
  widgets/         # shared, cross-feature widgets (state views, buttons, chips)
```

This is a strict layering convention: **Models → Repositories → Providers →
Screens/Widgets**. See `architecture.md` for details. A `features/<name>`
folder should not reach into another feature's `providers/` directly except
through things explicitly exposed for that purpose (e.g. `auth_providers.dart`
is read from almost every other feature to get the current uid/role).

## State management convention

Every feature exposes Riverpod providers from its own
`providers/<feature>_providers.dart` file:

- A `Provider<XRepository>` constructs the repository from
  `firestoreProvider`/other DI providers.
- `StreamProvider`s wrap repository streams (Firestore snapshots) for live
  data; `StreamProvider.autoDispose.family` is used for per-id detail streams
  so they don't outlive the screen that needed them.
- Plain `Provider`s derive filtered/combined view-state from other providers
  (e.g. `filteredPulseProvider`, `todayScheduleProvider`) so screens stay dumb
  renderers.
- Mutations go through an `AsyncNotifier`/`Notifier` controller (e.g.
  `AuthController`, `OrderDraftController`) exposing `AsyncValue` so buttons
  get loading/disabled state for free, and failures are parked as
  `AppFailure` in the controller's state.

## Routing convention

`lib/core/constants/routes.dart` is the single source of truth for path
strings — never hardcode a route string elsewhere. `lib/core/router/app_router.dart`
builds the `GoRouter`:

- A `redirect` callback gates screens by auth state and role
  (`UserRole.admin`/`isStaff`) — this is **UX only**; the real security
  boundary is Firestore rules.
- The four tab roots (Pulse/Map/Lost & Found/Printout) are nested inside a
  `StatefulShellRoute.indexedStack` hosted by `AppShell`, so each tab keeps
  its own navigation stack and scroll position when switching tabs.
- Detail screens are nested routes under their tab (e.g.
  `/map/location/:id`, `/print/order/:id`) so back-navigation stays within
  the tab.

## Error-handling convention

Screens never see raw Firebase exceptions. Every repository method wraps its
body in `FailureMapper.guard(...)`, which rethrows anything as an
`AppFailure` (see `architecture.md` for the full mapping). UI code calls
`describeFailure(e)` for a quick message or renders `AsyncValueView` /
`state_views.dart` widgets for a full error surface.
